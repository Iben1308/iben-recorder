# Iben Recorder 0.7.4 — перевірки

Дата: 2026-10-04. Версія: 0.7.4, versionCode 11.
База проєкту: 0.7.3; applicationId `ua.iben.recorder.oreo` збережено.

Користувач повідомив, що **попередня 0.7.3 працює на Android 8.1, 10 і 16,
а Bluetooth працює**. Нові зміни 0.7.4 тут на пристрої чи емуляторі не запускалися.
Ці два рівні перевірки не слід ототожнювати.

## Android-збірка

Java 17, Gradle 8.9, Android Gradle Plugin 8.7.3, Android SDK Platform 35
revision 2, Build-Tools 34.0.0, minSdk 27 / targetSdk 35.

Команда `:app:assembleDebug :app:assembleRelease :app:lintDebug :app:lintRelease`
завершилася **BUILD SUCCESSFUL**. Debug APK зібрано, release APK без підпису.
У кожному варіанті lint: **0 помилок, 35 попереджень**. Lint не вимикався;
baseline для приховування проблем не додавався.

CustomX509TrustManager належить перевірці явно імпортованого сертифіката;
зберігаються точний DER-збіг, строк дії, системна перевірка ланцюжка та hostname.
WakelockTimeout стосується наявного довготривалого RecorderService.
Нові служби операцій і підготовки відтворення мають обмежені wake lock.
Нові UsableSpace / SetTextI18n — рекомендації щодо місця й програмного UI.

Архів містить вихідний код, без APK, приватних ключів і паролів. Для оновлення
телефона потрібен той самий ключ підпису. Gradle запускається на JDK 17;
Java 8 у compileOptions залишається рівнем мови.

### Новий хмарний доступ

`CloudPlaybackTest` запускає production DavClient проти локального HTTP-сервера:

- PROPFIND Depth: 1, автентифікація, список без GET аудіо;
- UTF-8 / percent-encoding / `+`, прямі дочірні M4A, серверна дата й тривалість з назви;
- відхилення зовнішніх адрес, підпапок, неоднозначних шляхів, дубльованих ресурсів;
- відмова за DTD / зовнішніх сутностей, неповних властивостей і завеликого XML;
- обмежена HTTP-відповідь, Content-Length / chunked, відхилення неоднозначної довжини;
- HEAD, GET Range з If-Match, правильні байти при перемотуванні й на кінці файла;
- лише запитані байти для часткового читання, без повного завантаження;
- неправильний Content-Range, обрізана відповідь, змінений ETag, 412, стиснення;
- відмова від редиректів без витоку облікових даних;
- явний fallback для відповіді 200 на Range та повна копія з контролем розміру/версії;
- повторне читання з кешу, межа блоків, індекси буфера, EOF, скасування при зміні підключення;
- скасування заблокованого PROPFIND закриває сокет.

Для CloudAudioSource використана **лише абстрактна заглушка API MediaDataSource**.
Тест перевіряє власний буфер / HTTP-код, а не нативний Android-декодер.

Справжній HTTPS-сервер і тимчасові сертифікати keytool перевіряють production-шлях
ізольованої довіри. Новий PROPFIND проходить із правильним імпортованим сертифікатом;
системна довіра відхиляє самопідписаний, а імпортований сертифікат з неправильним
hostname не дозволяє надіслати HTTP-запит. Глобальні SSL defaults не змінюються.

Попередні тести передачі/видалення продовжують вимагати **нуль GET і нуль байтів
аудіо у відповідях**. Для явного прослуховування / експорту аудіо GET очікуваний.
Самопідписаний TLS на фізичному Android додатково потребує ручної перевірки.

### Видалення та база

FileUseRegistry перевірений реальними потоками: резервування відхиляє нових читачів,
скасовується лише вибраний запис, видалення очікує закриття lease. Таймаут або
переривання не дають дозволу видаляти відкритий файл; ресурс залишається захищеним.
Android MediaPlayer, MediaCodec і потоковий експорт через DocumentsProvider цими
тестами не запускаються. Зупинку їхніх реальних ресурсів слід перевірити на телефоні.

`check_database.py` виконує фактичні SQL-команди з RecordIndex на SQLite.
Міграції **v1/v2/v3/v4/v5/v6 → v7** зберігають усі старі поля, записи, типи
підтверджень, історію, важливість, закладки та наміри хмарного видалення.
Підтверджені копії переносяться в cloud_files; раніше завершене видалення не
стає наявною копією. Пізніше завантаження має пріоритет над старим знімком списку.
Перевірені окремі адреси/акаунти, збереження метаданих за наявності іншої хмарної
копії та цілісність бази після повторного відкриття. Це не запуск SQLiteOpenHelper
на Android; міграцію встановленої програми також перевірте на телефоні.

## Перегляд Android-коду та межі перевірки

Переглянуті MediaSession, audio focus, wakelock / Wi-Fi lock, історія позиції,
від’єднання Activity без зупинки програвача, фоновий експорт і групові дії,
скасування мережевих читачів, звільнення тимчасового файла, захист важливих записів,
локальне підтвердження fallback та відсутність автоматичного повтору DELETE після
загибелі процесу. Після ручного скасування передачі JobScheduler отримує завершення
завдання; номер сповіщення шкали більше не перетинається зі сповіщенням про збій запису.

**Не виконані instrumented-тести або запуск 0.7.4 на фізичному Android.**
Збірка й JVM-тести не доводять фонову роботу на конкретній прошивці. Потрібні
перевірки блокування екрана, керування MediaSession, тривалого Wi-Fi-стримінгу,
реального MediaDataSource/MediaPlayer, скасування MediaCodec, документного експорту,
системних обмежень Android 16, трьох мов і двох тем. План наведений у README.

Багатоденний запис, реальні стики AAC, SCO / BLE, Keystore і поведінка після
примусової зупинки в цьому середовищі не перевірені. Дані користувача та його
WebDAV-сервер не підключалися й не змінювалися. Особливості серверних прав,
кошика, reverse proxy, мобільного зв’язку та гарнітур залишаються предметом
перевірки на реальних пристроях.
